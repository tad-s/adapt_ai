# 運用とモデル改善の仕様

オペレーターのシフト作成に使うための、日々の運用手順と、予測モデルを育てていく仕組みをまとめる。

## 1. 運用サイクル

| タイミング | 作業 | アプリでの操作 |
|---|---|---|
| 毎週（シフト確定日） | 翌1〜2週間の予測を出し、シフトを決める | 「週間予測・シフト」タブ → 天気予報を自動取得 → 休日・気温を確認 → **予測を記録** → CSV出力 |
| 毎月初 | 前月の実績を追加し、再学習 | サイドバーで前月の集計表PDF/CSVをアップロード → **学習データとして保存**（再学習は自動） |
| 毎月初 | 精度の確認 | 「モデルの精度」タブ → 交差検証の精度と、**記録した予測の答え合わせ** |
| 年1回＋随時 | 会社独自の休日を登録 | `data/company_holidays.csv` にお盆休み・GW休業・創立記念日などを追加 |

## 2. データの保存場所

| ファイル | 内容 | 更新 |
|---|---|---|
| `data/calls.csv` | 日別実績（入電・応答・受付・休日・気温） | 毎月追加 |
| `data/company_holidays.csv` | 会社独自の休日 | 年1回＋随時 |
| `data/forecast_log.csv` | 出した予測の記録（予測日・何日前の予測か・使った気温・予測値・区間・学習データの最終日） | 予測を記録するたび |

将来、複数人で使う場合は、この3つのファイルを共有フォルダかデータベースに移す（アプリの読み書き先を変えるだけで済む構成にしてある）。

## 3. 精度の測り方（2種類）

1. **交差検証（モデルそのものの実力）**
    - 1か月ずつ抜いて学習し、抜いた月を当てる。実績の気温を使うので、天気予報の誤差は含まない。
    - 特徴量やパラメータを変えたときの比較に使う。
2. **予測記録の答え合わせ（本番での精度）**
    - 実際に出した予測（天気予報の気温を使った値）と実績を比べる。
    - 「何日前の予測か」ごとの誤差率と、80%区間に実績が収まった割合を見る。
    - 収まった割合が80%を大きく下回る場合は区間が狭すぎる → シフトを上振れ側で組む。

## 4. モデル更新のルール

- **再学習**: 実績を追加するたびに自動で行う（学習データが変わるとアプリがモデルを作り直す）。
- **改良の採用基準**: 特徴量の追加など、モデルの作りを変える場合は、「直近3か月をテスト期間にしたバックテスト」と「交差検証」の両方で、現行モデルより誤差が小さい場合だけ採用する。
- **異常日の扱い**: システム停止などで件数が0や極端に少ない日は、学習から除外する（現在は0件の日を自動で除外）。理由が分かっている日は、後述のイベント情報として記録しておく。

## 5. 段階的な拡張計画

| 段階 | 内容 | 必要なデータ | 効果 |
|---|---|---|---|
| 現在 | 日別件数を曜日・休日・気温で予測。業務量から1日の必要人数の目安を計算 | 日別実績（1年分） | 週・月単位の人数計画 |
| 第2段階 | 直近の実績（前週同曜日・直近7日平均）を特徴量に追加し、1〜14日先の予測精度を上げる | 日別実績を毎週更新 | 週間予測の精度向上 |
| 第3段階 | 時間帯別（30分/1時間単位）の予測と、アーラン式による時間帯別の必要席数 → シフト表の案 | 時間帯別の入電数、平均処理時間 | 時間帯ごとの過不足をなくす |
| 第4段階 | キャンペーン・製品トラブルなどのイベント効果をモデルに反映 | イベント履歴 | 突発的な急増への備え |

## 6. 精度向上に必要な情報（優先度順）

### A. 期間

- **最低2年、できれば3年以上の日別実績**。現在は1年分のため、「季節の影響」と「気温の影響」を切り分けきれない。同じ7月でも「猛暑の年」と「冷夏の年」のデータがあると、気温の効き方を正しく学べる。

### B. シフト作成に直結する情報

- **時間帯別の入電数**（30分または1時間単位）: 必要席数は1日の合計ではなく、ピーク時間帯で決まる。
- **平均処理時間（通話＋後処理）**: 必要人数の計算に使う。季節で変わる場合（夏は長いなど）は月別・時間帯別に。
- **放棄呼数・待ち時間**: 応答率が低い日は、かけ直しで入電件数が膨らむ。「本当の需要」と「かけ直し」を分けるのに使う。
- **その日の配置人数（シフト実績）**: 人が足りない日は応答率が下がり、かけ直しが増えるため、この関係をモデルに入れられる。

### C. 件数を動かす業務イベント

- キャンペーン、DM・チラシの発送日、新製品の発売、リコールや不具合の告知、料金改定
- システム障害・休業（0件だった 2023/4/8, 2023/10/21 の理由）
- テレビ・ネットでの露出、量販店の繁忙期（量販FAXの動き）
- ネット受付の開始・拡大（2024年1月以降、ネット受付件数が増えている）

### D. 気象

- **対象エリアの確定**: 主な顧客の地域。全国対応なら、主要都市の気温を顧客数で重み付けした値を使う。
- **観測値の出典の統一**: 学習データの気温と、予測に使う天気予報の気温を同じ地点にそろえる。
- 追加候補: 湿度・不快指数、熱中症警戒アラート、台風・大雪・寒波の情報。

### E. 事業の規模

- 販売台数・保守契約数など、問い合わせの母数の推移。年単位で件数が増減する傾向を説明できる。

## 7. 天気予報の取得仕様

- 取得元: Open-Meteo（無料・APIキー不要）。日別の最高・最低気温を最大16日先まで取得する。
- 直近7日分の気温も同時に取得し、「直近3日/7日の気温」の特徴量に使う。
- 地点はサイドバーで選ぶ（主要都市、または緯度・経度で指定）。
- 取得に失敗した場合は、過去実績の同時期平均（平年値）を入れて警告を出す。気温は表で手修正できる。
- 社内ネットワークで外部通信が制限されている場合は、`api.open-meteo.com` への HTTPS 通信の許可が必要。
